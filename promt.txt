TUJUAN PRODUK
Pengguna dapat membuat room, mengunggah video yang memiliki hak distribusi, memilih film, mengundang penonton, lalu menontonnya bersama. Semua perangkat menerima video dari media CDN/storage, tetapi playback dikendalikan satu server authoritative timeline. Play, pause, seek, switch movie, late join, buffering, refresh, dan reconnect harus otomatis ditangani tanpa sinkronisasi manual.

AUTHORITATIVE SYNC ENGINE
Setiap room aktif memiliki authoritative RoomCoordinator berbasis OTP. Coordinator memegang:
room_id, media_id, revision, status, anchor_position_ms, anchor_server_time_ms, playback_rate, effective_at_ms, pending_transition, duration_ms, control_mode, updated_at.
Semua posisi dibatasi antara 0 dan durasi media.
Rumus playing: position = clamp(anchor_position + elapsed_server_time * rate, 0, duration).
Paused berarti posisi dibekukan. Gunakan waktu UTC untuk serialisasi lintas perangkat dan monotonic clock untuk mengukur interval secara stabil.
Untuk operasi yang dijadwalkan di masa depan, state lama tetap berlaku sampai effective_at, lalu transition menjadi aktif.
Bangun queue/supersession policy yang deterministik agar command cepat berturut-turut tidak saling menimpa secara salah.
Coordinator wajib memvalidasi role, media readiness, session membership, dan command idempotency.
Gunakan revision monotonik, request_id, acknowledgments, snapshot dan recovery.
Persist state penting ke PostgreSQL termasuk posisi dan anchor wall clock; definisikan perilaku saat restart atau room tanpa peserta.
Untuk MVP gunakan satu Phoenix node; desain locking/ownership supaya tidak ada dua coordinator aktif untuk satu room saat nantinya multi-node.

CLOCK SYNCHRONIZATION
Client melakukan sejumlah ping dengan client send time, server response time, client receive time.
Estimasi RTT dan server clock offset menggunakan midpoint dan pilih sample RTT terbaik.
Refresh berkala, gunakan performance.now() untuk interval, pertimbangkan browser tab suspension dan system clock adjustment.
Tidak boleh memakai Date.now() mentah dari browser sebagai satu-satunya sumber kebenaran.
Server authoritative time harus dapat dipetakan ke client timeline secara konsisten.

SCHEDULED PLAYBACK
- Client hanya mengirim intent play, pause, seek, change media.
- Server menghitung state baru, effective_at masa depan, revision, kemudian broadcast.
- Lead time awal configurable, misalnya 1200 ms, dengan adaptasi terhadap RTT dan batas maksimum.
- Client yang menerima command sebelum T menyiapkan playback dan menjalankannya pada T.
- Client yang menerima sesudah T menghitung current authoritative position dan catch up.
- Jika command datang out of order, abaikan revision lebih lama.
- Tangani play() promise rejection, autoplay blocked, media not ready, stalled, interrupted seek, dan rejoin.
- Sediakan overlay Activate Player sebelum sesi film untuk mematuhi browser autoplay rules.

DRIFT CORRECTION
Implementasikan stateful drift correction controller.
Target_position berasal dari authoritative timeline.
Drift = actual_media_time - target_position.
Parameter awal:
- abs(drift) <= 200 ms: no adjustment.
- 200 sampai 1500 ms: soft correction menggunakan playbackRate secara terbatas, contoh 0.97 sampai 1.05.
- di atas 1500 ms: hard seek jika buffer dan readiness memungkinkan.
- Tambahkan smoothing, hysteresis, cooldown, dan batas frekuensi seek.
- Reset correction pada pause, seek manual oleh host, media replacement, ended, dan buffering.
- Jangan mengejar dengan playbackRate ketika buffer tidak cukup.
- Setelah reconnect, minta snapshot terbaru, abaikan state lama, seek ke canonical position dan resume jika diizinkan.
- Jangan mengklaim frame-perfect sync yang mustahil dijamin pada seluruh browser.
- Exposure metrics untuk drift p50/p95/p99, correction count, buffer count.

BUFFERING MODES
Implementasikan:
1. independent: peserta buffering recover sendiri tanpa menahan yang lain.
2. pause_all: coordinator menjadwalkan pause setelah kondisi buffering mencapai threshold, dengan grace period dan minimum affected participants.
3. host_decides: host melihat alert dan dapat memutuskan.
Ready/buffering event harus memakai debounce agar koneksi flapping tidak menyebabkan pause/play berulang.
Jika sistem melakukan auto-resume, pastikan seluruh peserta memenuhi readiness policy atau timeout yang masuk akal.

- Protected master playlist, variant playlist, video segments, subtitle dan thumbnails sesuai policy.
